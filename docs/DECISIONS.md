## 1. 임베딩 모델 선정

**후보**: Qwen3-Embedding-0.6B(최신 범용 모델이 이 도메인에서도 통하는지 검증용) /
BGE-M3(이미 검증된 강력한 baseline, sparse까지 지원해 나중에 하이브리드 확장 여지) /
KURE-v1(BGE-M3를 한국어로 추가 튜닝한 모델, "한국어 특화 튜닝이 실제로 이득인가"를
보는 핵심 대조군).

**결정**: KURE-v1. 세 후보 중 전 지표에서 1위 — 한국어 법률 도메인에서 언어별
파인튜닝이 뚜렷하게 유효함을 확인.

## 2. Chunking 전략

문서를 chunk로 쪼개 검색하면 성능이 오르는 것처럼 보였지만, 처음 실험은 "모델"과
"chunking 여부"를 동시에 바꿔서 원인을 알 수 없었음(confound). KURE-v1으로 모델을
고정하고 chunk 크기(200/500/1000자)만 바꿔 재검증한 결과 **chunking 자체가 지배적
요인**임을 확인, 짧게 자를수록 정확도가 좋아지는 경향도 확인.

이어서 overlap(청크 간 겹침) 유무를 추가로 검토 — overlap을 주면 공짜에 가깝게
정확도가 오르는 것을 확인. 정확도가 가장 좋은 조합(chunk 200자+overlap 50자)과,
정확도는 거의 동률이면서 DB 용량이 훨씬 작은 조합(chunk 300자+overlap 100자) 둘을
실제 pgvector에 적재해 최종 비교.

**결정**: `chunk_size=300, overlap=100`. 정확도 차이가 오차 수준으로 작은 반면 DB
용량은 크게 줄어, 용량 절감의 실익이 더 크다고 판단.

## 3. Vector DB 선택

**후보**: FAISS / pgvector.

**결정**: pgvector. 법률 판례 검색은 "법원명·사건종류·선고일자로 필터 + 의미 검색"을
같이 쓸 가능성이 높은데, pgvector는 이를 SQL 한 쿼리로 결합할 수 있고, 어차피 백엔드
단계에서 Postgres를 쓸 계획이라 인프라도 통합됨. 이 정도 데이터 규모는 FAISS만의
성능 우위가 필요한 스케일도 아니라고 판단.

## 4. 임베딩 모델 도메인 파인튜닝

Chunking까지 확정한 뒤, 검색 정확도를 더 올리기 위해 KURE-v1을 도메인 데이터로
추가 학습. 1단계(in-batch negative)만으로도 확실한 개선을 확인했고, 이어서
2단계(hard negative — 헷갈리는 오답을 의도적으로 학습에 섞는 방식)를 시도.

2단계 1차 시도는 오히려 1단계보다 성능이 나빠짐 — 원인은 "유사도 최상위 후보를
그대로 negative로 채굴"한 방식이 법률 도메인 특성(비슷한 법리를 인용하는 표준 문구가
많음)상 실제로는 관련 있는 문서까지 negative로 잘못 채굴(false negative)했기 때문으로
분석. 상위 몇 개를 건너뛰고 채굴하도록 수정 후 재학습.

**결정**: 수정한 2단계 모델을 최종 임베딩 모델로 채택. 1차 실패 → 원인 분석 → 수정 →
재검증까지의 과정 자체가 이 프로젝트에서 가장 명확한 "가설 검증" 사례.

## 5. Sparse(BM25) / Hybrid 검색 검토

법률 판례는 법조문 번호·고유명사처럼 키워드 매칭이 중요한 도메인이라는 가설로,
dense(의미 검색)에 sparse(키워드 검색)를 결합하는 하이브리드를 검토.

Postgres 내장 전문검색(tsvector)으로 먼저 구현했으나 이는 정식 BM25 공식(IDF·용어빈도
포화·문서길이 보정)이 아니라 성능이 약함을 확인 → IDF/k1/b를 실제로 계산하는 진짜
BM25로 재구현해 sparse 단독 성능을 크게 끌어올림. 그런데도 dense와 sparse를 여러
비율로 섞어(RRF) 정식 평가한 결과, **어떤 비율로도 dense 단독 성능을 넘지 못함**.

**결정**: retriever는 dense 단독으로 확정, 하이브리드는 미채택. "이미 도메인 파인튜닝된
dense 모델이 이 데이터셋에서 sparse가 보탤 여지가 없을 만큼 강하다"는 결론. 시도
과정과 구현(`SparseRetriever`/`HybridRetriever`)은 코드로 보존 

## 6. Reranker 도입

**후보**: ColBERT(late-interaction) / Cross-encoder.

ColBERT는 문서 하나당 토큰 수만큼 벡터를 저장해야 하는 구조라, 이 프로젝트의 코퍼스
규모에서 필요한 저장 공간을 계산해보니 이 인스턴스의 고정 디스크 용량을 훌쩍
넘어섬 — **저장 공간 예산 문제로 처음부터 배제**.

Cross-encoder(문서를 미리 인코딩해두지 않고 질문+후보를 그때그때 같이 인코딩하는
방식)는 추가 디스크가 거의 필요 없어 선택. 다만 처음에 기성(off-the-shelf) 모델로
평가했을 때는 오히려 dense 단독보다 성능이 나빠짐 — 범용 모델이 이미 도메인
파인튜닝된 dense의 1등 후보를 오히려 밀어내는 경우가 많았음(하이브리드 때와 같은
패턴). 그래서 임베딩 모델과 같은 전략으로 **reranker도 도메인 데이터로 파인튜닝**.

**결정**: 파인튜닝한 cross-encoder reranker 채택. 파인튜닝 후에는 dense 단독을
전 지표에서 확실히 상회 — 최종 검색 파이프라인은 "dense top-30 → 파인튜닝
reranker로 top-5 재정렬"로 확정.

## 7. 답변 생성 LLM 선정

**후보**: GPT류 API 기반 라우팅/생성 / 소형 로컬 오픈소스 모델.

**결정**: LG AI Research의 `EXAONE-4.0-1.2B`. 한국어 지원이 강하고 학습 단계에
agentic tool-use가 포함돼 라우팅 용도에도 적합하다고 판단. 더 가벼운 양자화(GGUF)
버전도 있었지만, GGUF는 파인튜닝이 불가능한 추론 전용 포맷이라 **나중에 직접
파인튜닝할 여지를 남기기 위해 원본 transformers 체크포인트를 그대로 사용**하기로 함
(디스크 여유를 확보한 뒤 결정).

## 8. 컨텍스트 구성 방식 (문서 전체 vs chunk)

**후보**: 검색된 top-5 판례의 **원문 전체**를 컨텍스트로 넘기는 방식 / **매칭된
chunk와 그 앞뒤**만 넘기는 방식.

GPT-5-mini를 LLM judge로 세워 두 방식을 사건유형 전체를 아우르는 표본으로 정식
비교한 결과, chunk 방식이 정확성·groundedness(할루시네이션 없음)·인용정확성·종합
평가 전부에서 우세. 원인으로는 소형 모델(1.2B)이 방대한 문서 전체를 한 번에 받으면
가끔 답을 아예 만들지 못하는 현상을 확인했고, 부가적으로 **문서 전체 방식은 코퍼스에
극단적으로 긴 문서 하나만 검색돼도 컨텍스트 크기가 모델의 최대 컨텍스트를 넘어
메모리 부족을 일으킬 수 있는 구조적 결함**도 발견.

**결정**: chunk(매칭 chunk + 앞뒤 1개씩) 방식 채택. 정확도, 안정성(메모리 부족 회피)
양쪽에서 문서 전체 방식을 택할 이유가 없다고 판단. (예외적으로 세무·특허처럼 여러
판례 간 세부 수치를 대조해야 하는 유형은 오히려 문서 전체가 유리하다는 신호도
있었으나, **유형별로 방식을 나누지 않고 모든 유형에 chunk 방식을 동일하게 적용하기로
최종 확정** — 예외 하나를 위해 파이프라인을 분기하는 복잡도를 들일 만큼 이득이 크지
않다고 판단.)

## 9. "답변 불가" 처리 조사

가설: reranker의 확신도 점수(cross-encoder 점수)로 "관련 판례가 없는 질문"을
걸러낼 수 있을 것.

실측 결과, 점수 분포만으로는 "확신 있게 틀린 경우"와 "제대로 맞은 경우"가 크게
겹쳐서 순수 threshold 하나로는 판별이 어려움. 이어서 "LLM이 스스로 판단해서
거절하게 하면 어떨까" 검증했으나, 실제로 거절한 사례의 대다수가 거절하면 안 되는
경우였음(LLM 자체 판단도 신뢰도 낮음). 더 나아가 GPT judge로 "라벨이 아니라 실제
검색된 문서 내용 기준 진짜 관련성"을 재확인한 결과, 정답 라벨과 다른 문서가
검색됐더라도 실제로는 거의 대부분 그 문서로 답변이 가능한 경우였음 — 즉 이 도메인
질문 분포에서는 "top-5에 쓸만한 판례가 아예 없는" 경우가 매우 드묾.

**결정**: "답변 불가 처리"라는 기능 자체의 실효성에 의문을 제기하고, LLM 자체 거절
로직은 보류. 대신 아주 낮은 확신도 threshold 하나만 "명백히 도메인 밖인 질문"을
거르는 저비용 안전장치로 남겨둠 — 애매한 영역은 걸러내려 하지 말고 항상 답변을
시도하는 편이 낫다는 결론.

## 10. 프롬프트 개선 시도 (실패 사례)

"질문이 정확히 무엇을 묻는지 먼저 파악한 뒤 답하라"는 다단계 지시를 프롬프트에
추가하는 개선을 시도. 소수 샘플에서는 의도한 대로 잘 작동하는 것처럼 보였으나,
전체 표본으로 정식 재평가한 결과 오히려 **전 지표에서 성능이 악화**됨.

**결론**: 원래(단순한) 프롬프트로 원복. 소형 모델(1.2B)은 지시가 복잡해질수록
핵심 과제(질문에 직접 답하기)에 쓸 여력이 분산되는 것으로 추정 — "작은 모델에겐
복잡한 지시보다 단순한 프롬프트가 낫다"는 교훈으로 기록. 개선 시도가 실패했다는
사실 자체도 실측으로 검증된 결과로 남김.

## 11. Reasoning mode 검토

EXAONE의 hybrid reasoning mode(모델이 답변 전에 스스로 사고 과정을 거치는 모드)를
켜서 응답 속도를 실측한 결과 일반 모드 대비 7~7.5배 느려짐을 확인.

**결정**: 정확도 검증 없이 최종적으로 채택하지 않기로 확정. 속도 비용이 이미
배포 목적(실시간 응답)에 맞지 않는다고 판단해, 정확도까지 따로 검증하는 추가 조사
없이 일반 모드를 그대로 서비스에 유지하기로 마무리.

## 12. 배포 인프라 선택

**후보**: AWS 등 별도 클라우드 신규 구축 / 지금 실험에 쓰던 Vast.ai GPU 인스턴스를
그대로 서비스로 전환.

**결정**: 기존 Vast.ai 인스턴스 그대로 사용. 이미 모델과 DB가 다 준비된 환경이라
비용과 실용성 면에서 새 인프라를 구축할 이유가 없다고 판단. FastAPI가 백엔드와
간단한 채팅 데모 페이지를 함께 서빙하도록 구성(디스크 여유가 빠듯해 Streamlit
같은 무거운 프레임워크 대신 선택), supervisor로 프로세스를 관리하고 기존 인증
프록시(Caddy) 뒤에 노출.

이후 배포 코드와 그동안의 실험/평가 스크립트가 한 폴더에 뒤섞여 있던 것을,
**실제 서비스 코드(`service/`)/생성 품질 실험 스크립트(`research/`)/양쪽이 공유하는
검색 평가 라이브러리(`eval/`)**로 분리 정리. 서비스 폴더에는 그동안 비교했다가
채택하지 않은 선택지(문서 전체 컨텍스트, reasoning mode, 되돌린 프롬프트 등)를 모두
뺀, 최종 채택 구성만 남긴 파이프라인 코드를 새로 작성.

## 13. 채팅 기능 확장과 이후 발견된 버그들

단발 질문-답변에서 나아가 "일반 챗봇처럼" 인사 등에도 자연스럽게 답하고, 답변에
대한 재질문도 처리할 수 있도록 라우터(이번 요청이 새 판례 검색이 필요한지 아니면
일반 대화/재질문인지 분류)와 멀티턴 대화 히스토리, 채팅 UI(말풍선)를 추가.

이 기능을 실사용해보는 과정에서 세 가지 버그를 추가로 발견해 수정:

- **라우터 오분류**: 실제 법률 질문 하나가 "일반 대화"로 잘못 분류돼 검색 없이
  근거 없는 답변이 나온 사례 발견 → 라우터 프롬프트에 예시와 "애매하면 검색을
  선택하라"는 편향을 추가해 수정.
- **한글 입력 시 답변 중복**: 한글은 마지막 글자를 조합 중인 상태에서 Enter를 누르면
  브라우저가 전송 이벤트를 두 번 발생시킬 수 있는데, 이를 구분하지 않고 있어 채팅이
  중복 전송되던 프론트엔드 버그 → 조합 중 이벤트를 무시하도록 수정.
- **무관한 대화에 대한 판례 조작(hallucination)**: 위 라우터의 "애매하면 검색"
  편향 때문에 순수한 잡담성 입력에도 검색이 걸리는 경우가 생기는데, 이때 검색
  결과가 명백히 무관한데도 모델이 그 결과를 무시하고 자기가 학습 때 외운 그럴듯한
  가짜 판례번호로 답을 지어내는 사례 발견 → 9번 항목에서 조사해뒀던 확신도
  threshold를 실제 서비스 코드에 연결해, 확신도가 threshold 미만이면 검색 결과를
  쓰지 않고 "관련 판례를 찾지 못했습니다"로 확정 응답하도록 안전장치를 추가.

## 14. 프로젝트 스코프 최종 확정

채팅 기능까지 완성하고 버그를 수정한 시점에서, 그동안 미뤄뒀던 항목들의 진행 여부를
한 번에 정리해 프로젝트를 마무리 지었다.

- **reranker hard negative 개수 ablation은 폐기**: "hard negative를 줄이면 오히려
  나빠질 것"이라는 추측만 있었고 실측 근거가 없던 아이디어라 더 이상 추진하지 않기로 함.
- **Phase 4 백엔드 고도화(세션 저장, 입력 검증/에러 처리, 로깅/모니터링, rate
  limiting, 스트리밍 응답, Docker 패키징, AWS 등 별도 클라우드 배포)는 스코프
  아웃**: 지금 배포된 상태(FastAPI + 채팅 기능, 기존 Vast.ai 인스턴스에 supervisor로
  서비스)를 이 포트폴리오 프로젝트의 최종 완성 지점으로 간주하고, 위 항목들은
  의도적으로 진행하지 않기로 결정.
- **사건번호 정규식 라우팅 / MMR(다양성 재정렬) / 메타데이터 필터 결합은 future
  work로 유보**: 위 두 항목과 달리 완전히 접은 건 아니고, 지금 스코프에서는 진행하지
  않되 나중에 여유가 되면 재검토할 수 있는 백로그로 남김.
